PROJECT_SPEC — "The Culprit"

Personal academic website + embedded Calendly widget & admin-only appointment log for an information-security professor.
Status: v1.0 — In development Owner: Project team Calendly: Free, embed-only Auth: Single admin

01 Project Overview

"The Culprit" is a personal academic website for a professor whose field is information security. It presents the professor's work publicly and gives the admin a simple, direct way to record and manage their own appointments.

The product has two halves:

  • Public info — bio, research, publications, and team members (incl. visiting professors). Design reference: the UCL profile of Lorenzo Cavallaro.
  • Appointment system — descoped 2026-08-08 (see §2 NG2/NG6): no visitor request form, no review queue, no server-side link between the two ways a meeting can happen. A visitor can book a slot via the embedded Calendly widget (NEXT_PUBLIC_CALENDLY_URL), but that booking lives entirely on Calendly's side and never reaches this app. Separately, the admin can directly declare an appointment (name, optional email, optional research group, time, optional topic) in Manage Appointments — that is the only way a row is ever created in this app's database. Lifecycle transitions are scheduled → cancelled (reason required) and scheduled → scheduled (reschedule, time-only). Updated 2026-08-13 (ADR-010): admin can also hard-delete any appointment (audited, any status) — see §5.4 FR-22.

Design language: professional, minimalist, information-security aesthetic. See §9 for the current (2026-08-05) Figma-derived visual system: fixed dark-navy header, mono numbered indices, colored-dot status badges.

Elevator pitch: A clean public presence for a security researcher, plus a lightweight, admin-only appointment log. Visitor booking runs entirely on Calendly's free embed — no server-side sync, because Calendly's Free plan doesn't support one.

02 Goals & Non-Goals

Goals

  • G1 — Professional, minimalist public presence (bio, research, publications, team members).
  • G2 — Visitors book directly (30-min default) or request a meeting, no account (name + email only). Descoped (2026-08-08): a visitor can still book via the embedded Calendly widget, but that's Calendly's own flow, entirely outside this app — see NG6. No in-app request form exists.
  • G3 — Admin fully controls: approve, decline, cancel requests; edit all content. Reworded (2026-08-08): admin directly declares and cancels appointments (no review queue) and edits all public content.
  • G4 — Durable record of every admin-declared appointment + status change (cancellations soft, retained). Updated 2026-08-13: admin may also hard-delete a record outright (audited) — see FR-22, ADR-010.
  • G5 — Embed the Calendly widget so visitors can book directly against availability, independent of this app's own records.
  • G6 — Clean, modular architecture reusable across future apps.

Non-Goals

  • NG1 — Direct booking is handled by the Calendly widget itself; the app does not auto-create, capture, or sync a Calendly booking in any way. No Calendly API supports programmatic booking creation on any plan, and (per NG6) no server-side integration exists at all to capture bookings after the fact either.
  • NG2 — No real-time Calendly sync / webhooks. History: briefly superseded 2026-08-02 by a server-side Calendly REST integration (PAT client, read event-types/events/availability, admin cancel-with-sync, signature-verified webhook receiver). Reverted 2026-08-08 and removed outright: Calendly webhook subscriptions require the Standard tier or above — the Free plan has no webhook access on any tier — so the receiver could never actually fire without a paid upgrade. Reverted to the original NG2 stance: embed only. See §14.2 and src/modules/integrations/calendly/README.md.
  • NG3 — No public user accounts / logins / visitor profiles.
  • NG4 — No multi-admin, no per-researcher self-editing in MVP (single admin).
  • NG5 — No payments, chat, or extra content-approval workflows.
  • NG6 (new, 2026-08-08) — No server-side link between a Calendly embed booking and this app's Appointment table, and no appointment review/approval queue. An appointment row exists only because the admin typed it into Manage Appointments directly. See §10.1.

03 Scope

In Scope (MVP)

  • Public site: About, Research, Publications, Team Members, Upcoming Events (admin-gated), Make Appointment (current 6-tab layout, see §9.1 note, 2026-08-05).
  • Research groups & visiting professors (CV-style: works & achievements), via Team Members.
  • Direct booking via embedded Calendly widget — Calendly's own flow, not recorded in this app.
  • Admin directly declares appointments (name, optional email, optional research group, time, optional topic) via Manage Appointments — no requester-facing form or approval step.
  • Admin panel: Set Information + Manage Appointments.
  • Lifecycle: scheduled → cancelled only (admin-declared, admin-cancelled, reason required).
  • Embedded free Calendly widget on the public tab only; single admin auth; no appointment notification emails.

Out of Scope / Future

  • F1 — Paid-Calendly auto-book + webhook sync. Moot: no approval/webhook path left to auto-book into. Superseded by F1a: reintroducing a visitor-facing request/review queue, should that be wanted later.
  • F2 — Multiple admins / roles; researcher self-service editing.
  • F3 — Public search / tagging / filtering of publications.
  • F4 — Analytics dashboard, multi-language, dark/light user toggle.
  • F5 — Native mobile apps.
  • F6 (new, 2026-08-08) — Appointment confirmation/cancellation emails to the requester; removed with the notifications module.

10 Workflows

10.1 Appointment lifecycle (rewritten 2026-08-08)

Two flows exist and do not talk to each other (see §2 NG6).

A — Visitor books via Calendly embed (not recorded in this app):

  1. Visitor opens Make Appointment, picks a slot in the embedded Calendly widget.
  2. Calendly confirms the booking directly to the visitor by email. Nothing is written to this app's Appointment table — no webhook, polling, or capture of any kind.
  3. If the professor wants that meeting to show up in this app, they add it manually, per flow B.

B — Admin declares an appointment directly (the only way a row is ever created):

  1. Admin opens Manage Appointments, clicks Add.
  2. Fills requester name (required), email (optional, informational only — no email is sent), research group (optional), scheduled time, topic (optional). Saves.
  3. System stores it as scheduled immediately — no approval step, no intermediate state.
  4. Admin may Edit a scheduled appointment's details, or Reschedule it (time-only, scheduled → scheduled, audited) at any time. 409 if not currently scheduled.
  5. Cancellation: admin clicks Cancel, supplies a reason → cancelled. Record retained (soft); no email is sent. 409 if already cancelled.
  6. Visibility: admin toggles is public (isPublic) on any row to show/hide it on the public Upcoming Events tab, independent of status. (2026-08-13, ADR-010)
  7. Deletion: admin clicks Delete on any row (any status) → hard-deleted, audited via AuditLog (full before-state) prior to removal. Separate from cancel; not reversible. (2026-08-13, ADR-010)
History: the previous design (through 2026-08-05) had visitors submit a request that the admin approved/declined, then manually booked in Calendly and marked booked, with a notification email at each step. That entire review-queue workflow — and the appointment notification emails — were removed 2026-08-08. See §5.2, §5.4, §7.1.

10.2 Content edit

  1. Admin opens Set Information, edits a form.
  2. Clicks Save changes → API validates and persists → success feedback.

10.3 Upcoming-events visibility toggle

Rewritten 2026-08-13 (ADR-010): was a single global toggle in Set Information; now per-appointment.
  1. Admin toggles is public on an individual row in Manage Appointments.
  2. Public Upcoming Events tab shows or hides that specific meeting accordingly (only scheduled + isPublic rows are ever listed).

One R2 bucket holds every category (profile/research/publications/ events/documents), split by folder prefix rather than one bucket per category. documents stays private, but R2 has no per-prefix ACL the way Supabase RLS did — privacy is now enforced entirely by which method application code calls (getSignedUrl vs getPublicUrl), never by storage-side policy. Accepted as a low-risk simplification for a single-admin site.

12.2 Module boundaries

  • content — profile, research, publications, research-groups (incl. TeamMember) (read public, write admin).
  • appointments — admin-declared create/update/cancel/reschedule/delete, per-row isPublic visibility, audit trail. No request intake (removed 2026-08-08).
  • auth — single-admin session management (Better Auth, DB-backed cookie sessions).
  • settings — deleted 2026-08-13, ADR-010 (was: the global upcoming-events-visible feature flag). Upcoming Events visibility is now Appointment.isPublic, owned by the appointments module — there is no separate settings module or Setting model anymore.
  • notifications — deleted 2026-08-08 (was: email on appointment status transitions). No appointment email of any kind is sent by this app anymore.
  • integrations — Calendly (embed-only as of 2026-08-08 — no server-side client, no webhook receiver, no PAT), Cloudflare R2 storage adapter (switched from Supabase Storage 2026-08-08 — see §14.1), YouTube embed helper, Turnstile bot-challenge (active as of 2026-08-08 — gates visibility of the public Calendly embed via /api/turnstile/verify), email provider (Resend; unused for appointments).
  • Rate limiting (replaced 2026-08-10 — see §14.1) — no longer Upstash/Redis. A Cloudflare WAF rule at the edge throttles admin login; a small in-process fallback (no external store) covers login and admin mutation routes if that edge rule is ever off. Public GET routes aren't rate-limited — caching absorbs that traffic instead.

  • Validation + rate-limiting at the API edge.
  • Audit logging in the service layer.

14.1 Stack (adopted)

Note (2026-08-05): Option A below is no longer just a candidate — it is the adopted, running stack. Prisma connects via @prisma/adapter-pg (a plain pg Pool) over Supabase's pooled Postgres connection (port 6543, pgbouncer), not @prisma/adapter-neon. Supabase Auth was evaluated and explicitly rejected for admin auth — the project kept Better Auth (single-admin, DB-backed cookie sessions, not JWT) to avoid running two competing auth systems, since the existing single-admin design already fit; prisma/seed.ts provisions the admin account from ADMIN_EMAIL/ADMIN_INITIAL_PASSWORD.
Update (2026-08-08) — storage reversed from Supabase Storage to Cloudflare R2: the prior "Option B's Cloudflare/R2 combination was evaluated and not taken" note is superseded for storage specifically — R2 is now adopted for object storage, driven by a hosting-cost review (HOSTING_COST.html, dated 2026-08-07): Supabase Storage's free tier caps egress at 5GB/month, which becomes the binding bottleneck around ~650 visitors/day even though expected load is ~100/day; R2 never charges for egress. Database stays on Supabase Postgres — only the object store moved, so the adopted stack is now a hybrid of Option A (DB, auth, hosting) and Option B (storage only), not a full switch to B. R2_PUBLIC_URL is deliberately the bucket's free pub-<hash>.r2.dev dev URL, not a custom domain on culprit.wyco-dev.com — that domain's DNS zone lives in a different Cloudflare account than the one holding the R2 bucket, so a custom-domain public URL would need a CNAME coordinated across two separate account logins; the .r2.dev URL needs no DNS at all. See src/modules/integrations/storage/storage-adapter.ts.

Rate limiting moved off Upstash (2026-08-10, ADR-008): the app-level Upstash/Redis limiter is gone. Admin login (POST /api/auth/sign-in/email) is now throttled by a Cloudflare WAF Rate Limiting Rule (5 requests/10s per IP, blocked at Cloudflare's edge before reaching the app), the one rule the Cloudflare Free plan allows per zone. A small in-process, in-memory limiter (no external store) is the fallback layer behind it, also covering mutating /api/admin/** routes. Reason: removes a Redis dependency that existed only for rate limiting, and moves the highest-value protection (login brute force) in front of the app instead of after it.
Cloudflare edge caching added (2026-08-12, ADR-007 addendum): the six public GET API routes and public pages are now cached at the Cloudflare edge too, in addition to Next's own cache. A Cloudflare Cache Rule on culprit.wyco-dev.com respects each route's own Cache-Control header. Each route sends an explicit two-tier header: a short browser TTL and a longer edge TTL (e.g. max-age=300, s-maxage=3600 for most content; max-age=60, s-maxage=300 for the time-sensitive upcoming-events route). An admin save triggers a Cloudflare purge for the affected paths (optional, only runs if CLOUDFLARE_API_TOKEN/CLOUDFLARE_ZONE_ID are set) in addition to Next's own cache invalidation, so a stale edge-cached page can't outlive an edit by more than the purge round-trip.
